**The two join facts a buyer gets wrong on this dataset:**

1. `fr_nagpra_title_index.csv` is **neither a subset nor a superset** of
   `nagpra_notices.csv`. Its regex omits *"notice of intended disposition"*, so
   168 notices are in the product and not in the index; 2 documents are in the
   index and not in the product, having no cached full text. They are two
   different cuts of the same corpus. Use the product for notices and the index
   only for corpus-level coverage over time.
2. The `*_entity_ids` columns on `nagpra_notices.csv` are **pipe-delimited
   lists**, not join keys. The bridge is the join.

`tribe_id` is the advertised entity key on the bridge and it validates: 568
distinct values, **0 of them absent from `data/spine/cedar_entity_spine.csv`**.
`cedar_uid` is **not** advertised on this dataset and is not currently present —
see §5.

## 1. FETCH — the Federal Register full text

```
py -3 code/77_build_nagpra_dataset.py fetch
```

Resumable and idempotent: it reads the notice universe out of
`data/clean/federal_actions.csv`, skips every document already in the cache, and
pulls only the rest. 2 workers / 0.55 s, inside the envelope this host has been
run at without throttling.

- Cache: `data/raw/federal_register/nagpra_fulltext/<year>/<document_number>.txt.gz`
  — 6,772 files, 17 MB. **The cache holds GPO's markup INTACT on purpose.**
  An earlier version cleaned before caching and destroyed the `<bullet>` tokens
  that separate the MNI finding from the affiliation finding. Clean at build
  time, never at fetch time.
- Documents with no plain-text rendition return 404 and are listed in
  `review/nagpra_unparsed.csv` with reason `no_cached_full_text`. There are 2.
  They are not a failure; the PDF is still in `pdf_url`.
- `fetch` writes a `.fetchmeta` sidecar recording retrieval time. Where no
  sidecar exists — every document cached before 2026-08-30 — `fetched_date` is
  emitted as **empty**, and that is deliberate. Do not fill it from the file's
  mtime: an mtime is set by whichever of download, copy, extract or rsync
  touched the file last, and deterministically wrong provenance is worse than
  deterministically missing provenance. The mtime is emitted separately under
  its honest name, `artifact_mtime`.

**Upstream first.** The notice universe is cut from `federal_actions.csv`, so a
fetch can only see notices that corpus already holds. Refresh it first:

```
py -3 code/342_pull_federal_register_incremental.py
```

## 2. NORMALIZE + 3. RESOLVE IDENTITIES + 4. ENRICH — all inside the build

```
py -3 code/77_build_nagpra_dataset.py build          # ~3 min, no network
py -3 code/78_content_analysis.py --nagpra-only      # ~40 s, no network
```

There is no separate normalize or resolve stage. Both happen inside `77 build`,
and both are worth knowing about before you run it:

- **Normalization** is `clean_fr_text()`: `<bullet>` becomes a real bullet so the
  determination findings can be split, Cloudflare's email obfuscation collapses
  to a placeholder, tags are stripped, entities are unescaped. Line breaks and
  indentation are the Federal Register's own and are preserved — the section
  detector depends on them.
- **Identity resolution** is `resolve_entity` from
  `code/33_apply_party_rulings.py`. That is the project's ONE resolver
  (standing rule 8) and nothing here re-implements matching. What 77 adds on top
  is refusals and post-hoc acceptance tests, never a second matcher.
- **Nothing is written to `data/spine/`.** Names that look like real historical
  tribe names but do not resolve go to `review/nagpra_alias_proposals.csv`
  (1,048 today) for the recognition-history work and for Elijah.

### Why `--nagpra-only` and not a plain `78`

`build.py plan nagpra` lists `78_content_analysis.py` as a phase-1 rebuilder.
It is — but it writes **18 tables and only three of them belong to this
collection.** A full `78` run rewrites `lobbying_issue_families_filing.csv` from
scratch, and that file carries five columns 78 does not produce: `cedar_uid`
(from `503_identity.py`) and the four `entity_id_withdrawn*` columns (from
`353_propagate_lobbying_corrections_to_consumers.py`). Running the plan end to
end destroys another collection's enrichment and trips
`62.files_with_columns_lost_vs_backup`, which must be zero.

`--nagpra-only` runs the same classifiers and holds every write back except the
three nagpra-side outputs. Both orderings are declared in
`cedar_pipeline.KNOWN_ORDERINGS`, so this is not folklore.

> **Do NOT run `py -3 code/build.py run nagpra --execute`** until the plan's
> phase 1 for this collection is `78 --nagpra-only`. The scoreboard prints that
> command as the generic rebuild entry point; for this collection the two
> commands at the top of this section are the rebuild path.

## 5. The one enricher that must run AFTER a rebuild

```
py -3 code/503_identity.py stamp --apply
```

`503_identity.py` discovers its tables at RUNTIME — it stamps `cedar_uid` into
every `data/clean` CSV carrying one of 18 entity-id columns — so no static scan
can attribute it and `build.py plan nagpra` shows **zero** phase-2 enrichers for
a table it demonstrably edits.

**This ordering has been paid.** 503 stamped `nagpra_notice_entity_bridge.csv`
on 2026-08-28 (`.bak_2026-08-28_pre505` is the receipt) and the 2026-08-29
rebuild reverted it. The shipped bridge today has 14 columns and no `cedar_uid`,
and the reason its clean-room replay is byte-identical is that **the enricher's
work is currently absent**, not that the plan reproduces it.
`cedar_pipeline.columns_lost_vs_backup` cannot see this, because the newest
backup IS the pre-505 state and the live table matches it.

Two consequences, both deliberate:

- No promise is broken. The bridge's advertised join key is `tribe_id`, which
  validates on the full file. `cedar_uid` is not in this dataset's contract.
- If you want it back, run the command above **after** the build, never before.
  It stamps ~96 tables, so run it when no other workstream is mid-build.

`nagpra_notices.csv` also shows an enricher-backup warning
(`.bak_2026-08-26_pre_342_nagpra_refresh`, on both tables). **It is not an
enricher backup.** It is a hand-taken safety copy:
`342_pull_federal_register_incremental.py` names its own backups
`pre_342_pull_federal_register_incremental`, never mentions NAGPRA, and writes
only `federal_actions*.csv`. `nagpra_notices.csv` carries no entity-id column, so
503 skips it too. **Nothing enriches `nagpra_notices.csv`.** The warning is
noise and the file is left in place rather than deleted; do not re-investigate.

### Row conservation (contract point C5) — and the one way it breaks

Every source row this dataset reads lands in a NAMED disposition bucket. The
ledgers are written by 77 and 78 into `review/nagpra_row_conservation.csv` and
merged into `data/clean/cedar_harvest_conservation.csv`, the file 510's
invariant **I13** and `62.harvest_rows_unaccounted` already gate:

| table | rows read | dispositions |
|---|---:|---|
| `nagpra_notices.csv` | 156,772 | 6,772 emitted · 149,998 title is not one of the four NAGPRA notice headings · 2 no cached full text |
| `nagpra_notice_entity_bridge.csv` | 51,994 | 50,774 emitted · 734 trap guard: narrative prose, not a party name · 357 trap guard: place name or trap word · 129 duplicate of an earlier span |
| `fr_nagpra_title_index.csv` | 156,772 | 6,644 emitted · 150,128 title does not carry a NAGPRA notice heading |
| `fr_nagpra_title_index_year.csv` | 6,644 | 6,644 emitted |

Read `rows_in` for the first three as *every row of `federal_actions.csv`* and
*every fragment the span parser cut out of a tribe-list span*. The title filter
is itself a drop, and it is the drop this dataset is built on, so it is counted
where it happens rather than reconstructed by subtraction.

**The failure mode.** `py -3 code/510_assertions.py all --apply` REWRITES
`cedar_harvest_conservation.csv` from its own ledgers only, and will delete
these ten rows. If `62` reports `harvest_source_rows_read` falling, or 518 puts
`nagpra` back to BLOCKED on C5, the repair recomputes nothing:

```
py -3 code/77_build_nagpra_dataset.py conservation
```

That re-publishes `review/nagpra_row_conservation.csv` into the shared file,
merging — every other ledger's rows are preserved verbatim.

Proof the check works, rather than an assertion that it does:

```

```

It injects three breaches (coverage deleted, `rows_in` inflated so rows vanish
