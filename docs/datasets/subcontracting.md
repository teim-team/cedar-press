### Why a closed year still moves

FSRS filings arrive years after the action date. Measured on one FY2021
subaward: **93 separate SAM reports on a single $57,500 subaward, filed monthly
from 2022-08 through 2025-01.** So "we pulled FY2019 once" is not the same claim
as "we hold FY2019", and a re-pull of a closed window is not a duplicate pull.
`fy2025_refresh` and `fy2026_refresh` exist for exactly this, and they are
deduped by `m45.identity_key` rather than stacked — re-reading a window is
idempotent by construction.

## 3. THE ROW KEY — measured 2026-09-01, and it cuts both ways

`code/525_event_ids.py` registers subcontracting as the **one dataset that
genuinely lacks an event id**, and closes: *diagnose the source extract first.*
Diagnosed, at zero network cost, on extracts already on disk.

**The source HAS a unique row id, and the mapper drops it.**

* The FSRS extract carries **121 columns**. `94_match_raw_subawards.build_row`
  reads **26** of them. Ninety-five are dropped.
* `subaward_sam_report_id` is one of the dropped ones, and it is a UUID that is
  **globally unique**:

| | rows | distinct `subaward_sam_report_id` | blank |
|---|---:|---:|---:|
| FY2021, both zip members | 765,109 | **765,109** | 0 |
| FY2020, both zip members | 456,412 | **456,412** | 0 |
| FY2020 ∩ FY2021 | — | **0 overlap** | — |

This is the `prime_contracts` shape exactly: 80,778 "duplicates" there turned
out to be distinct transactions whose `modification_number` the mapper never
carried.

**AND YET THE DE-DUPLICATION IS SUBSTANTIVELY RIGHT.** A unique id on the row
does not make the rows distinct subawards:

* `m45.identity_key` collides on **111,933 of 765,109** FY2021 raw rows (14.6%).
* The worst group is **93 rows**. All 93 carry distinct
  `subaward_sam_report_id` values. Their `subaward_sam_report_month` values run
  2022-08 through 2025-01, on **one** $57,500 subaward with one action date and
  one subaward number.
* They are **93 monthly re-filings of one subaward**, not 93 subawards.
  Counting them would inflate the year by roughly 14.6% of rows.

So `subaward_sam_report_id` identifies **a SAM subaward REPORT, not a
subaward**, and the two grains must not be confused:

| if you want | the key is | status |
|---|---|---|
| one row per SAM **report** | `subaward_sam_report_id` | exists in the source, **not carried** |
| one row per **subaward** | `m45.identity_key` plus `duplicate_status == 'primary'` | carried, and correct |

**Do NOT mint a surrogate over `subaward_sam_report_id` and call it a subaward
id.** 525's warning still binds: the id is real, but it counts reports.

**What carrying the three report columns WOULD buy**, and why it deserves a
later pass: `duplicate_status` is today *inferred* from a six-field tuple and
cannot be checked against the source without re-reading a 1.2 GB zip. With
`subaward_sam_report_id`, `subaward_sam_report_month` and
`subaward_sam_report_last_modified_date` on the row, it becomes auditable, and
"is this a re-filing or a second subaward?" becomes a lookup instead of an
argument.

**Not done in the 2026-09-01 run, deliberately.** It changes the grain
declaration of a shipping table and belongs with whoever owns
`code/525_event_ids.py` and the schema, not with a puller.

### Other columns the mapper drops that this source would give us

## 4. HOW TO REFRESH, AND WHAT NOT TO RUN

```
py -3 code/121_pull_subawards_api.py canary            # ~9 min, one 2-day job
py -3 code/121_pull_subawards_api.py pull --only <jobs>
py -3 code/121_pull_subawards_api.py collect           # resume accepted tokens
py -3 code/121_pull_subawards_api.py match
py -3 code/121_pull_subawards_api.py append            # the enricher, runs LAST
py -3 code/250_demote_stale_tierA_subaward_rows.py     # the other 2b enricher
```

* **Buy the cheap answer first.** `canary` is one two-day job. On 2026-08-12 the
  API returned HTTP 200 and a token for nine consecutive submissions and built
  none of them. An accepted token is not a working job.
* **`45_promote_subawards.py` CANNOT promote a 121 pull, and running it is
  destructive.** It reads only
  `data/raw/subcontracts/usaspending_subawards_2026-08-05` and cannot see
  `usaspending_2026-08-12/`; it would re-stamp `source_dataset` on rows it
  re-reads, and write 49 columns, reverting the deflator enrichment. The route
  for anything 121 pulls is **`121 match` then `121 append`**. The generated
  `02b_subcontracting.md` still says to run 41 then 45; that instruction is
  stale for this pull path.
* One poller per host, ever — `docs/PULL_DISCIPLINE.md`. Check with
  `Win32_Process.CommandLine`; `ps aux` cannot see command lines on Windows and
  has returned 0 with four pullers live.
