## What changed in this run

Two defects were fixed. Both were real, both are demonstrated below rather than
asserted.

1. **The pull stopped inside its first keyword.** The v1 run had completed 460
   of 517 pages of the single term `tribe` and had not begun the other 215
   terms. Because the API returns filings in ascending date order, an
   interrupted sweep does not look interrupted — it looks like a dataset that
   ends in 2008. The v1 clean CSVs were a snapshot taken at that point.
2. **The alias matcher compared the two name registers in one direction only**
   and therefore could not see six- and seven-figure tribal filers whose names
   it should have recognized on sight.

## The host moved, and the old one is past its sunset date

The v1 code targeted `lda.senate.gov`. That API's own OpenAPI document
(`/api/openapi/v1/`) carries an RFC 8594 sunset declaration:

> **Sunset:** Fri, 31 Jul 2026 23:59:59 GMT — a new unified API is available at

Today is 2026-08-05. The old host still answers, but it is five days past its
announced end of life and can stop at any time. v2 targets `lda.gov/api/v1/`,
which serves identical payloads and returns no deprecation headers. **Anything
built on the `lda.senate.gov` host from here on is building on a fuse.**

## How the pull works

Three properties of this API had to be measured rather than assumed, and all
three change how the job must be run.

1. **`page_size` is capped server-side at 25.** Requesting 100 returns 25 and a
   `next` link that still walks in 25s. The `tribe` sweep is therefore 517
   requests, not 130.
2. **The anonymous throttle is 15 requests/minute.** Re-measured on `lda.gov`
   during this run: 13 requests succeeded in 12.3 seconds and the 14th returned
   HTTP 429 with `Retry-After: 33`. The documented figures are 15/min anonymous
   and 120/min with a registered API key. Pacing is interval-based
   (start-of-request to start-of-request), which holds ~14 req/min with zero
   429s across the whole run; a fixed post-request sleep silently loses the
   ~1.2s request latency and lands at ~11 req/min.
3. **`client_name` is a token-PREFIX match, not a substring match.** Query
   "ribe" returns RIBERA DEVELOPMENT LLC, not the "tribe" filings.

**Getting an API key is the single highest-return improvement available here.**
It is a free signup at `lda.gov/api/register/` and it multiplies throughput by
eight. It requires a human to complete the registration, so it is not something
this run could do for itself.

### The three-stage design, and why v1's shape could not finish

v1 ran 216 keyword sweeps against `/filings/` and paginated each in full. That
is correct and enormously wasteful: the 204 specific-name terms overlap the 12
broad terms almost completely, and every overlapping page costs a throttled
request against a 15/min ceiling. v1 was still inside keyword 1 of 216 after 35
minutes of running.

v2 keeps every guarantee v1 had — append-only raw file, dedupe on `filing_uuid`,
per-page progress checkpoint, resume from wherever it stopped — and adds a
client-first discovery stage that makes the redundancy **exactly computable**
instead of guessed:

| stage | endpoint | scope | purpose |
|---|---|---|---|
| 1 | `/filings/` | 12 broad terms | bulk retrieval, 25 filings per request |
| 2 | `/clients/` | all 216 terms | the client roster is one to two orders of magnitude smaller than the filing roster, so this is cheap; it yields the exact `client_id` set each term resolves to |
| 3 | `/filings/?client_id=` | clients Stage 1 provably never touched | Cherokee Nation, Koniag, NCAI, Kamehameha Schools — names carrying no generic Native token |

The Stage-3 coverage test is exact, and this is the load-bearing claim: **if a
client is returned by `/clients/?client_name=K`, and `K`'s `/filings/` sweep ran
to completion, then every filing of that client was returned by that sweep** —
both endpoints apply the same `client_name` filter. So Stage 3 only has to fetch
what the broad nets could not reach, and it uses the API's own matcher to decide
that, not a local re-implementation of its tokeniser.

**Resume safety.** `raw_filings.jsonl` is append-only and every `filing_uuid`
already on disk is loaded into a dedupe set at startup, so re-running never
duplicates a row. Three progress files (`pull_progress.json`,
`client_progress.json`, `clientfetch_progress.json`) record per-keyword and
per-client state, so an interruption resumes at the next unfetched page rather
than restarting a 517-page sweep. This run in fact resumed a v1 pull mid-keyword
at page 461 and lost nothing.

## How the match works, and what it refuses to do

The binding constraint on this dataset is entity resolution, not retrieval. The
posture is the one in `AGENTS.md`: match conservatively, leave ambiguous blank
and flagged. Name similarity is not relatedness.

the client name. The two sides are written in different registers:

| `YUROK TRIBE` | Yurok Tribe of the Yurok Reservation, California |
| `MOHEGAN TRIBE OF CONNECTICUT` | Mohegan Tribe of Indians of Connecticut |
| `ST REGIS MOHAWK TRIBE` | Saint Regis Mohawk Tribe |
| `ONEIDA TRIBE OF INDIANS OF WISCONSIN` | Oneida Nation *(renamed 2015)* |
| `CONFEDERATED TRIBES OF THE GRAND RONDE OF OREGON` | Confederated Tribes of the Grand Ronde Community of Oregon |

The canonical string is **longer** than the client string in five of these six,
so it cannot be contained in it. The short alias that *would* be contained
("Hopi", 4 characters, 1 token) sits below the ≥12-character / ≥2-token
containment floor — a floor that exists for a good reason, since it is what
stops the bare token "cherokee" from ever being a usable alias.

### The fix

Normalize **both sides** and compare token sets, so the direction of the extra
words stops mattering.

- `norm()` — casefold; `&`→`and`; drop apostrophes (`o'odham`→`oodham`); dashes
  and punctuation → space; expand the abbreviations that actually occur in the
  data (`st`→`saint`, `ste`→`sainte`, `ft`→`fort`, `mt`→`mount`); expand a
  trailing two-letter USPS code (`of OK`, `in KS`).
- `glue_initials()` — merge a stray single-letter token into the next one, so
  `COEUR D' ALENE` and `COEUR DALENE` meet. A one-letter token never carries
  identity, and the rule is applied to both sides.
- `core()` — drop STRUCTURAL words (tribe / tribes / nation / band / indian /
  indians / community / reservation / rancheria / pueblo / village /
  confederated / council / of / the …) and peel a **trailing** state qualifier
  iteratively.

Position matters in that last step and getting it wrong is expensive. An earlier
draft stripped state names *anywhere* in the string. That silently emptied the
stem of every tribe whose own name is a state word — **Colorado River** became
`{river}`, **Iowa Tribe of Kansas and Nebraska** became `{}`, **Delaware
Nation** became `{}` — a large and completely invisible class of false
negatives. States are peeled in trailing position only, where they are a
jurisdictional qualifier, never in leading or medial position, where they are
the identity.

### Seven guards, each written because it caught a specific wrong answer

Loosening the comparison without loosening the standard of proof is the whole
job. None of these were written in the abstract; every one is named after a
wrong answer the matcher actually produced on the pulled data.

- **G1 — contested single token.** A one-token stem is usable only if that token
  appears in the stem of at most two canonical entities. Measured on the 687-row
  table: `cherokee` = 11 entities, `creek` = 14, `sioux` = 13, `paiute` = 24,
  `chippewa` = 21 — all contested, all refused. `hopi` = 1, `mohegan` = 1,
  `yurok` = 2, `oneida` = 2 — distinctive, allowed. This is the Cherokee Inc.
  trap and the Berry Creek trap expressed as a **measurement on the entity
  table** rather than as a hand-maintained blocklist. `CHEROKEE TRIBE` is
  refused; `BERRY CREEK RANCHERIA` resolves to Berry Creek and not to any
  Creek nation.
- **G2 — ambiguity refuses.** A stem resolving to two or more entities matches
  nothing. The state tiebreaker may resolve such a set **only** when the client
  name itself carries an explicit state and exactly one candidate sits in it:
  `ONEIDA TRIBE OF INDIANS OF **WISCONSIN**` against Oneida NY and Oneida WI.
  That is decisive evidence in the name, not a coin flip. With no state in the
  name, `ONEIDA NATION` stays unmatched and `KICKAPOO TRIBE` stays unmatched
  with all three Kickapoo governments listed.
- **G3 — leading-qualifier conflict** (inherited from v1). A distinctive token
  standing *before* the stem that belongs to another entity's vocabulary refuses
  the match: `ABSENTEE SHAWNEE` is not the Shawnee Tribe. Tokens standing
  *after* the stem are descriptors and do not refuse.
- **G4 — containment needs two tokens.** A single-token stem is only ever
  matched by exact stem equality, never by containment. `NAVAJO NATION
  WASHINGTON OFFICE` does not silently become the Navajo Nation; it goes to the
  review queue with its one candidate named.
- **G5 — sibling family.** A containment alias can resolve to one entity at the
  surface while its stem belongs to a family of distinct governments.
  `SAC FOX NATION MESKWAKI TRIBE` matched the Sac and Fox Nation of **Oklahoma**
  on the alias "sac fox nation" — but Meskwaki is the Sac & Fox Tribe of the
  Mississippi in **Iowa**. The stem `{sac, fox}` belongs to three separate
  federally recognized tribes. G3 could not catch it: `meskwaki` stands after
  the alias and appears nowhere in the canonical table, so there was nothing for
  it to conflict with. The match is now refused unless the client name carries
  evidence that separates the family — an explicit state, or a token owned by a
  proper subset of it (`WHITE MOUNTAIN **APACHE**` against the Alaska village
  that shares the "white mountain" stem).
- **G6 — nickname underspecification.** `canonical_name` and `biatld_nameshort`
  are short forms, and a short form can be a common place name.
  `PUEBLO OF SAN JUAN` — New Mexico, now Ohkay Owingeh — matched
  `TRBF-SNJUAN-00`, the **San Juan Southern Paiute Tribe of Arizona**, on the
  nickname "San Juan". Two different tribes in two different states. The check:
  take the head of `entity_namefull` (everything before its first " of ") and
  require that the client stem not be a strict subset of it. The Arizona tribe's
  head is "San Juan Southern Paiute Tribe" and the client said neither
  "southern" nor "paiute". Hopi, Yurok, Mohegan, Grand Ronde, Quechan and
  Colorado River all pass unchanged, because their client stems equal their head
  stems exactly.

- **G7 — a second government named in the same client string.** Two shapes,
  both found in the pull. `PUEBLO OF TESUQUE AND PUEBLO OF POJOAQUE` is one LDA
  client naming two separate pueblos; the matcher took the longer alias, booked
  the filing to Pojoaque and silently dropped Tesuque. And the entity ids encode
  parent/band structure — `TRBF-MINNCH-00` is the Minnesota Chippewa Tribe,
  `CNSF-MINNCH-FL` is its Fond du Lac component band — while the parent's own
  `entity_namefull` enumerates all six bands, so the parent picks up aliases
  that *are* the bands. `FOND DU LAC BAND` booked to the parent while
  `MILLE LACS BAND` was refused by G5: the same question answered two different
  ways. Both now go to the queue. Disjoint token spans are what keep this from
  firing on mere nesting — "shawnee tribe" sits inside "eastern shawnee tribe of
  oklahoma", but it overlaps, so it is nesting and not a second entity.

Two additional data-hygiene fixes found in the entity table itself:

- `entity_namefull` for `CNSF-NAVAJO-RM` is
  *"Navajo Nation, Arizona, New Mexico, & Utah – Ramah Navajo Chapter"*. v1's
  unconditional "drop everything after the last comma" rule turned that into
  "Navajo Nation, Arizona, New Mexico", **manufacturing a "Navajo Nation" alias
  for the Ramah Navajo Chapter** and sending the single largest tribal filer in
  the data to the ambiguity queue. The comma tail is now dropped only when every
  token in it is a state name or structural filler, which is the only case the
  rule was ever meant for.
- `confederate` is accepted as structural. LDA filers type it for
  "confederated" (`CONFEDERATE TRIBES OF THE CHEHALIS RESERVATION`), and it
  carries no identity either way.

`anc_tribal_subsidiary_lookup.csv` carries `parent_entity_id` values that do not
exist in `canonical_tribe_table.csv` — they are alternate ids for entities the
spine already holds under different ones:

| asserted in subsidiary file | actual spine id | entity |
|---|---|---|
| `TRBF-WBGNON-00` | `TRBF-WNNBGO-00` | Winnebago Tribe of Nebraska |
| `TRBF-CHKSAW-00` | `TRBF-CHKSWN-00` | Chickasaw Nation |
| `TRBF-CHCNAO-00` | `TRBF-CTWNAT-00` | Choctaw Nation of Oklahoma |
| `TRBF-CSAKT-00` | `TRBF-CSKTFR-00` | Confederated Salish & Kootenai |

| `TRBF-PRCHCK-00` | `TRBF-POARCH-00` | Poarch Band of Creek Indians |
| `TRBF-FCPCMM-00` | `TRBF-FSTCTY-00` | Forest County Potawatomi |
| `SGVF-TLNGHD-00` | `AKNF-TLNGHD-00-SEALSK` | Central Council of Tlingit & Haida |
| `NHO-MANUKAI-00` | *(unresolved — NHOs are not in the 687-row table)* | Manu Kai LLC |

Left alone this splits a single government across two ids in the panel and
quietly halves both sides. **Ho-Chunk Inc** — the project's gold-standard
verified case — booked to the phantom `TRBF-WBGNON-00` while the Winnebago
Tribe of Nebraska itself booked to `TRBF-WNNBGO-00`. The parent **name** is now
resolved through this same matcher rather than hand-mapped, so the remap is
auditable and is printed in the run log; the one that does not resolve is kept
as asserted and flagged rather than dropped. Ho-Chunk Inc and the Winnebago
Tribe now share one entity id, which is the check that says this worked.

Legal-form suffixes get the same two-sided-but-asymmetric treatment as
everything else: `incorporated`→`inc`, `corporation`→`corp`, `limited`→`ltd`
are normalized on both sides so `KONIAG INC` reaches "Koniag, Incorporated",
but the suffix is **never deleted from the client name**, because "HO-CHUNK
INC" minus "INC" is "Ho-Chunk" — the name of a different tribe. A
suffix-dropped surface form is generated on the entity side only, and only when
two or more tokens remain, which is what stops "Sealaska Corporation" and
"Koniag, Incorporated" from collapsing to a bare token.

Every matched row records `matched_alias` (the exact normalized string that
matched) and `attribution_method` (which tier fired), so every attribution in
the output is reconstructable from the output alone.

### What the guards cost, stated plainly

The before/after table in the stats block lists every client v1 matched that v2
now refuses. They are not regressions to be fixed; each is a guard doing its
job, and each is named in the review queue with its candidates. Two of them are
worth knowing about specifically:

- The **Minnesota Chippewa Tribe** component bands — Mille Lacs, Leech Lake,
  Grand Portage, Fond du Lac, White Earth — appear both inside
  `TRBF-MINNCH-00`'s own `entity_namefull` and as their own `CNSF-MINNCH-*`
  rows. v1 silently booked them all to the parent. Whether a Mille Lacs Band
  filing belongs to the Band or to the Tribe is a real attribution question with
  a real answer, and it is one ruling that resolves five entities at once.
- **G6 is deliberately over-strict.** It sends `CONFEDERATED TRIBES OF COOS`
  and `WALKER RIVER INDIAN TRIBE` to review — both are recognizable to a reader
  — in order to stop `PUEBLO OF SAN JUAN` from being booked to a different
  tribe in a different state. That trade costs a rounding error of attributed
  spend and buys a class of error that is invisible once it is in the data.
  Precision over recall is the house rule and this is what it looks like when
  it is actually applied.

## Spend accounting

LD-2 reports carry **either** `income` (an outside registrant billing a client)
**or** `expenses` (a self-filing entity reporting its own in-house lobbying
costs). They are never summed. `spend_basis` records which field produced the
figure and `self_filed` flags filings where the registrant is the client. This is
the hygiene point from `LOBBYING_DATA_PLAN.md`: for self-filers, registrant
expenses are the measure and client income is blank.

## Known gaps

These are properties of the source and of this run's scope, not defects to be
quietly patched over.

1. **Self-filers report expenses, not income.** Kept in separate columns in the
   panel (`spend_from_client_income_usd` vs
   `spend_from_registrant_expenses_usd`). Do not add them and call the total
   "lobbying spend" without saying which is which.
2. **The $3,000/quarter de minimis threshold.** Registrants whose income from a
   client falls below the reporting threshold, and organizations whose in-house
   expenses fall below it, need not report a dollar figure. Small entities are
   systematically under-observed in spend and can be absent from the filing
   record entirely.
3. **This run is a NAME net only.** `docs/plans/INFLUENCE_DATASET_PLAN.md` calls for three
   nets: name, issue-code (Indian/Native American Affairs and gaming), and the
   LD-1 affiliated-organizations field. Only the name net has been pulled. The
   issue-code net is what produces the **counter-lobby layer** — non-Native
   clients filing on Native issues — and it is deliberately absent here.
   `affiliated_organizations` is captured on every matched row as a free
   hierarchy signal but has not been used as a discovery net.
4. **LD-203 contributions are not pulled.** Separate endpoint, separate build.
5. **Keyword-net recall is bounded by naming.** A tribally owned entity whose
   client name carries no Native token and is not in the specific-name list is
   invisible to this pull. Same undercount direction as the `hci_analysis.do`
   finding in `AGENTS.md`.
5b. **The net also over-collects, and the raw match rate reflects that.** The
   API matches on token PREFIX, so short specific-name terms collide:
   `pala` reaches PALANTIR TECHNOLOGIES, `indian community` reaches IVY TECH
   COMMUNITY COLLEGE OF INDIANA and COMMUNITY HEALTH NETWORK INDIANAPOLIS,
   `regional corporation` reaches NORTHEAST ILLINOIS REGIONAL COMMUTER
   RAILROAD. None of them match an entity, which is the matcher working, but
   they sit in the denominator. **70.5% of all pulled filings match; 78.8% of
   filings whose client carries a Native token match.** The second number is
   the one that describes entity resolution; the first also describes how wide
   the net was cast. Both are in the stats block.
5c. **Spend, not tokens, is what finds the non-obvious names.** The review queue
   therefore includes every unmatched client above $1M regardless of whether its
   name looks Native. That is what surfaces NANA DEVELOPMENT CORPORATION
   ($4.9M), DOYON UTILITIES, KAMEHAMEHA SCHOOLS ($2.6M) and TUBA CITY REGIONAL
   HEALTH CARE — real Native entities carrying no Native token, exactly the
   undercount class named in `AGENTS.md`. Ruling out PALANTIR costs a human two
   seconds; missing NANA Development costs the dataset $4.9M.
6. **LDA filer typos are not repaired, by design.** The residual contains
   `SAULTE STE MARIE`, `MICCOUSUKEE`, `CHEHAILS`, `TIMBISHE`, `PUEBLO OF
   POJAQUE`, `PUEBLO OF JAMEZ`, `EWIAAPAAYP`, `HABERMATOLEL`. Every one is a
   recognizable federally recognized tribe to a reader and none is reachable
   without edit-distance matching, which this project does not do. They are
   routed to `review/lobbying_ambiguous_2026-08-05.csv` for a ruling instead of
   being guessed at. This is the largest single remaining recall gap and it is
   cheap for a human to close.
7. **Akas missing from the entity table.** `GUN LAKE TRIBE OF POTTAWATOMI
   INDIANS` is the Match-e-be-nash-she-wish Band; `PUEBLO OF SAN JUAN` is Ohkay
   Owingeh. Neither aka is in `canonical_tribe_table.csv`, and Ohkay Owingeh's
   `fedreg_nameprev` is blank where it should carry "San Juan Pueblo". Fixing
   the table fixes the match permanently, and is the right place to fix it.
8. **Intertribal organizations are not single tribal governments and are not
   matched.** SCTCA, ANTHC, USET, CERT, NCAI, Inter-Tribal Timber Council,
   NATHPO and similar are correctly left unmatched. They are a real and
   separately interesting population, not residue.
9. **Attribution is to the named client only.** No parent/subsidiary rollup
   beyond what `anc_tribal_subsidiary_lookup.csv` already asserts, and no
   time-aware ownership attribution.
10. **The API is a live index.** Counts drift as filings post and amend; the
    `tribe` sweep counted 12,743 on 2026-05-01 and 12,910 on 2026-08-05. Row
    counts are as-of the run date.
11. **The unmatched file is output, not residue.** Clients flagged
    `native_token_hit=1` are the individually-Native-owned firms, unlisted
    enterprises, intertribal organizations not yet in the entity spine, and the
    adjacency universe. No ruling has been made on any of them here.

## The review queue

`review/lobbying_ambiguous_2026-08-05.csv` follows the reconcile-queue protocol
in `AGENTS.md` (issue_type, evidence, question, `YOUR_RULING`). It carries two
kinds of client:

- **Guard refusals** — the matcher could have produced an answer and declined
  to. `competing_entity_ids` lists every candidate. Issue types:
  `ambiguous_multiple`, `ambiguous_sibling_family`, `generic_single_token`,
  `nickname_alias_underspecified`, `single_token_core_needs_ruling`,
  `qualifier_conflict`, `state_conflict`, `ambiguous_subsidiary`.
- **No-candidate Native clients with real money** — `no_alias_hit` clients
  carrying Native tokens and non-zero spend. These are the typos, the missing
  akas, and the intertribal organizations. `competing_entity_ids` is empty
  because no candidate was proposed; the question asks which of the four
  possibilities applies.

Rulings imported from this file become permanent per-entity decisions, the same
jurisprudence model as the per-UEI drops in `hci_analysis.do`.
